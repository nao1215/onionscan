# Benchmarks

onionscan is measured the way a user runs it, one process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds onionscan, runs each command in interleaved rounds, and reports latency, CPU time, peak RSS and, for the large input, throughput.

```console
$ go install github.com/nao1215/himorime@latest
$ make bench            # himorime run bench
$ make bench-compare    # himorime compare --against main bench
```

## Regression suite: himorime.yaml

`make bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v0.2.3 make bench-compare` compares against another revision. `himorime run --filter 'compare 100k' bench` measures one benchmark.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

Nothing in the suite reaches the network, and HOME and the XDG directories point into the benchmark's own directory, so the scan history and configuration of your machine are neither read nor changed. The scan history `compare` reads is generated by `gen.sh` before measuring (it runs the Go program in `gendb/`, which writes two scans through onionscan's own database code), so no fixture is added, and both revisions run the working tree's `gen.sh`.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `onionscan version` | starting onionscan |
| `compare 10` | `onionscan compare`, with `--json`, with `--markdown` | comparing two stored scans of 10 findings, where start-up and opening the database dominate |
| `compare 100k` | `onionscan compare`, with `--json`, with `--markdown` | reading and decoding two stored scans of 100 000 findings each, matching new, resolved and unchanged findings, and writing each format |
| `compare error` | `onionscan compare` on a service with no history | the error path of compare, exit 1 |
| `scan error` | `onionscan scan` on an address that is not a v3 onion address | reading the flags and the configuration, opening the database, and failing before Tor is started, exit 1 |

Not measured:

| Command | Why |
|---------|-----|
| `onionscan scan` on a real service | A scan starts Tor (or connects to a Tor SOCKS proxy), builds circuits and crawls a live onion service; its time is the network's, and the suite does not reach the network. A local stand-in would have to be a SOCKS5 proxy and web server running beside onionscan for every run, which a himorime hook cannot keep alive; the E2E suite (`make e2e`) covers this path instead. |
| `onionscan init` | It writes a starter configuration file and does no scanning or reporting. |

Numbers from different machines are not comparable; compare revisions on one machine, as `make bench-compare` and CI do.
